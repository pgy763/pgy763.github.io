这一套东西是怎么来的

三份内容各自为什么长成这样、验证到什么程度、哪些结论被代码纠正过。

写下来是因为：一个项目对自身边界的描述，比它的功能列表更能说明问题。

起点

我先写的是书。动机很具体：照着文档把第一个接口调通之后，真正的问题才开始—— 流式输出为什么在网关后面变成一次性返回、工具调用为什么偶发参数解析失败、 超时该设多少、重试为什么会让费用翻倍。

这些问题在「快速开始」里都看不到，因为那部分文档只需要证明它能跑。 所以第一件事是补「能调通」和「能上生产」之间那段。

三份内容，三种形态，各自的取舍

接入手册：先有能跑的模块，才有那一章

15 章，配 12 个可运行的 Spring Boot 模块。约束是自己定的： 没有可运行示例的章节不写。因为纯文字的接入教程已经够多了，缺的是「跑起来是这样」。

范围上做了收缩：只讲 Spring AI 和 LangChain4j，不追求覆盖所有框架。 选型对比单独放在第一章，配三种可运行的实现，让读者自己比较，而不是听结论。

踩坑手册：按报错索引，不按知识体系

51 条。组织方式和书相反——不按章节顺序，按报错关键词。 理由很实际：半夜查错误的时候，没有人会先通读目录。

每条固定三段：报错原文（或现象）、为什么、怎么改。 配图的处理也定了一条规矩：能拿到真机截图的用真机截图， 拿不到的按该条报错原文渲染成图，并在条目里标注—— 不把渲染图冒充成终端截图，这种便宜占了会让整份材料的可信度打折。

完整项目：把限制写出来，而不是藏起来

shopkeeper-agent 是「怎么做」的那一份：FastAPI + LangGraph，12 个节点， 三路异构召回，生成—校验—纠错闭环。

它有一页 已知限制， 列的是没有鉴权、没有限流、SQL 直接执行、重建不幂等这类问题。 写这一页的动机不是自曝，而是：不说清楚边界，读者会以为它能上线， 然后在真正要用的时候发现不是——那比没有这个项目更糟。

第四件：从「读」到「拦住」

手册解决的是「已经报错了怎么办」。但更省事的是别踩进去。所以挑出最贵的十条 （事务里调模型、单例 ChatMemory、直接注入 ChatClient、SSE 没设超时、流式里 block、 text/event-stream 缺 charset、maxTokens 太小、空 catch 吞 IO、 HTTP 客户端没配超时、硬编码密钥），做成了一个独立工具： llm-lint。

它是纯静态扫描，不需要 classpath、不联网、不要 API key。这三点是有意的 —— 要能塞进 pre-commit 和 CI，就不能依赖「先把环境跑起来」这个前提。

写的底线是宁可漏报、不可乱报：没有符号解析，类型只按声明的文本判断，链式调用一律不追。 判断不了就沉默，不猜。

验收方式是 20 个样本文件：samples/bad 里每个文件必须只触发它自己那条规则， samples/good 里的修复版必须一条都不报。CI 两个方向都跑 —— 少报会红，乱报也会红。

验证到什么程度

这是我认为最该交代的一张表。绿色勾不是重点，最后一列才是：

项目自动验证逐条核对没有验证
接入手册 CI 构建 12 个模块 + 站点部署 每章示例在本机跑通 换厂商、换模型的差异
踩坑手册 索引脚本生成 51 条、站内搜索、部署 每条对照真实报错与相关代码 版本差异（条目里已标注「措辞可能因版本而异」）
llm-lint CI：10 个反例各报一条、10 个正例零报告、两方向都卡 在 llm-gateway、prompt-ops 两个真实项目上跑过，0 误报 样本之外的写法、跨文件类型推断
shopkeeper 无 CI、无测试 文档里每条结论对着代码读过 端到端问数（需要 1.3 G 向量模型和一个可用的 key）
llm-gateway CI：13 个状态机测试 本地 mvn verify HTTP 层、限流、降级链
prompt-ops CI：仅编译打包 本地 mvn package 12 个接口没有任何单元测试
Blog- 无 CI 本地 mvn package 通过 运行期行为（需要 MySQL / Redis）

「有 CI」不等于「测过」。prompt-ops 的 CI 只保证能编译， 它 12 个接口的正确性目前完全依赖人读代码。

被代码纠正过的几处

写文档最大的副产品是：不得不逐行对代码，然后就发现原来的说法是错的。 这几条都改回了文档里：

「字段变了重跑一次就好」是错的

shopkeeper 的三处存储重建行为完全不同：Meta 表主键是固定的 表名.列名，重跑直接主键冲突； Qdrant 的向量点 id 是 uuid4()，重跑不会覆盖而是累积重复； 只有 Elasticsearch 的文档 id 是确定值，天然幂等。原来的 README 一句话带过，会让人踩坑。

「校验 SQL」节点在 SQL 语法错误时也上报 success

因为它上报的是「校验这个动作执行成功了」，而不是「被校验的 SQL 正确」。 所以前端不能拿这个事件判断 SQL 对不对，终态只能看 result / error。

配置里写了，代码里没读

es.index_name: data_agent 改了不生效——代码里硬编码了 value_index。 这类「配置项看起来能改、实际不起作用」的问题，只读 README 永远发现不了。

README 写着「需要 JDK 17+ 和一个 JDK」

句子重复。小问题，但它暴露的是：这份 README 写完没有回头读过一遍。

CI 第一次跑就挂了：退出码 126

llm-gateway 的 mvnw 是在 Windows 上提交的，索引里记的是 100644， Linux Runner 上执行不了。修法是把权限位写进仓库（git update-index --chmod=+x）， 而不是让每个人本地 chmod。

第一条规则写完，先被自己的正例打回来了

LLM003 最初只要字段类型是 ChatClient 就报。可正例里那些用 ChatClient.builder() 自己造出来的字段也被报了 —— 那恰恰是最推荐的写法。 口径后来收紧成「带注入注解的才报」。没有正例的规则，只算写了一半。

站点仓库名少了一个前缀，根路径一直是 404

用户站点必须叫 <用户名>.github.io。原来的仓库叫 .github.io， 所以 https://pgy763.github.io/ 根本不存在——直到给仓库改名。

这套东西不是什么

  • 不是生产代码。没有鉴权、没有限流、没有灰度，写它是为了把过程讲清楚。
  • 没有真实用户数据。shopkeeper 的示例库是造的，数字不对应任何真实业务。
  • 不是 benchmark。没有任何「方案 A 比方案 B 快 30%」这类量化结论，因为我没做过对照实验。
  • 结论有版本边界。AI 生态半年一变，所有涉及具体行为的地方都只在这些版本上验证过。
为什么要把这些写出来。 一份材料如果只讲它有多好，读者没法判断该不该信； 讲清楚它在哪一步停下、哪一步没验证，反而更容易被正确使用。
